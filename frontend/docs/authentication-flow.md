# Frontend Authentication Flow

## Overview

The Kora Frontend authentication flow allows users to register and log in through the API Gateway.

The Frontend does not communicate directly with the Identity microservice. All authentication requests are sent through the API Gateway, which forwards them to the corresponding Identity endpoints.

The authentication flow includes:

- User registration.
- User login.
- Access token management.
- Refresh token management.
- Automatic token renewal.
- Session cleanup.
- Safe authentication error handling.

---

## Architecture

The authentication communication flow is:

```text
Frontend
   ↓
API Gateway
   ↓
Identity Microservice
   ↓
API Gateway
   ↓
Frontend
```

The API Gateway is the only backend entry point used by the Frontend.

The default Gateway URL is:

```text
http://localhost:8000
```

The Frontend configuration is defined in:

```text
frontend/js/kora-config.js
```

## API Gateway Configuration

The Frontend uses the API Gateway as its backend entry point.

The default API base is:

```javascript
var API_BASE =
  global.KORA_API_BASE_URL ||
  "http://localhost:8000";
```

Authentication endpoints are configured in:

```javascript
endpoints: {
  identityHealth:
    "/api/identity/users/health/",

  register:
    "/api/identity/users/register/",

  login:
    "/api/identity/users/login/",

  refresh:
    "/api/identity/users/token/refresh/"
}
```

The final request URL is generated by combining:

```text
API_BASE + endpoint
```

For example:

```text
http://localhost:8000
+
/api/identity/users/login/
```

results in:

```text
http://localhost:8000/api/identity/users/login/
```

# Registration Flow

## Registration Route

The Frontend sends registration requests to:

```http
POST /api/identity/users/register/
```

The complete development URL is:

```text
http://localhost:8000/api/identity/users/register/
```

---

## Registration Request

The Frontend sends:

```json
{
  "email": "user@example.com",
  "password": "Password123!",
  "first_name": "Test",
  "last_name": "User",
  "date_of_birth": "2000-05-20"
}
```

The request is sent using:

```javascript
KoraApi.registerUser(payload);
```

The API method is:

```javascript
async function registerUser(payload) {
  return request(
    cfg().endpoints.register,
    {
      method: "POST",
      json: payload
    }
  );
}
```

---

## Registration Validation

Before sending the request, the Frontend validates:

- Required fields.
- Email format.
- Password minimum length.
- Password confirmation.
- Terms acceptance.
- Empty or whitespace-only values where applicable.

A request is not sent when the local validation fails.

---

## Successful Registration

A successful registration response contains user information.

The Frontend displays:

```text
Cuenta creada correctamente. Redirigiendo...
```

The user is then redirected to:

```text
initial_setup.html
```

---

## Registration Errors

Registration errors are converted into controlled Frontend messages.

Examples:

```text
No fue posible registrar la cuenta con los datos proporcionados.
```

```text
Se realizaron demasiados intentos. Inténtalo nuevamente más tarde.
```

```text
El servicio no está disponible temporalmente. Inténtalo nuevamente más tarde.
```

Raw backend exception information is not displayed.

# Login Flow

## Login Route

The Frontend sends login requests to:

```http
POST /api/identity/users/login/
```

The complete development URL is:

```text
http://localhost:8000/api/identity/users/login/
```

---

## Login Request

The Frontend sends:

```json
{
  "email": "user@example.com",
  "password": "Password123!"
}
```

The request is sent using:

```javascript
KoraApi.loginUser(
  email,
  password
);
```

---

## Successful Login Response

A valid login response must contain:

```json
{
  "success": true,
  "data": {
    "user_id": "user-id",
    "access": "access-token",
    "refresh": "refresh-token"
  }
}
```

The Frontend explicitly verifies that:

```text
success === true
```

and that both tokens exist:

```text
access
refresh
```

If any required authentication value is missing, the response is not considered a valid login.

---

## Login Session Creation

After successful authentication, the Frontend extracts:

```text
user_id
access
refresh
```

and stores them using:

```javascript
KoraApi.setSession(
  userData,
  accessToken,
  refreshToken
);
```

The user then receives:

```text
Sesión iniciada. Redirigiendo...
```

and is redirected to:

```text
app/main_panel.html
```

# Token Strategy

## Current Strategy

The current authentication backend returns the access and refresh tokens in the login response body.

The Frontend stores the authentication state using browser storage.

The following storage keys are defined:

```javascript
storageKeys: {
  user: "kora_user",
  token: "kora_token",
  refreshToken: "kora_refresh_token"
}
```

The stored values are:

```text
kora_user
kora_token
kora_refresh_token
```

---

## Centralized Token Access

Pages should not directly access:

```javascript
localStorage.getItem(...)
```

for authentication tokens.

Token access is centralized through:

```javascript
KoraApi.getToken();
```

and:

```javascript
KoraApi.getRefreshToken();
```

Session information is accessed through:

```javascript
KoraApi.getUser();
```

This keeps token handling inside the API/session layer.

---

## Access Token Usage

Before sending an API request, the request helper checks whether an access token exists.

When available, it automatically adds:

```http
Authorization: Bearer <access_token>
```

Example:

```javascript
headers.Authorization =
  "Bearer " + token;
```

Individual Frontend pages therefore do not need to manually create authentication headers.

# Refresh Token Flow

## Refresh Route

The refresh token is sent through the API Gateway using:

```http
POST /api/identity/users/token/refresh/
```

The complete development URL is:

```text
http://localhost:8000/api/identity/users/token/refresh/
```

---

## Refresh Request

The Frontend sends:

```json
{
  "refresh": "refresh-token"
}
```

using:

```javascript
KoraApi.refreshAccessToken();
```

---

## Automatic Access Token Renewal

When a protected request returns:

```text
401 Unauthorized
```

and a refresh token exists, the Frontend attempts to renew the access token.

The flow is:

```text
Protected API request
        ↓
401 Unauthorized
        ↓
Refresh token available
        ↓
POST /api/identity/users/token/refresh/
        ↓
New access token
        ↓
Store new access token
        ↓
Retry original request
```

The original request is retried only once.

---

## Retry Protection

The refresh request uses:

```javascript
retryOnUnauthorized: false
```

This prevents recursive refresh attempts.

The original protected request is also retried with refresh disabled.

This avoids infinite authentication loops.

---

## Expired or Invalid Refresh Token

If the refresh token is invalid or expired:

```text
Access token invalid
        ↓
Refresh attempt
        ↓
Refresh rejected
        ↓
clearSession()
```

The Frontend removes:

```text
kora_user
kora_token
kora_refresh_token
```

The user must authenticate again.

---

# Session Cleanup

Session data is removed through:

```javascript
KoraApi.clearSession();
```

This removes:

```text
User data
Access token
Refresh token
```

Logout actions use the same centralized session cleanup mechanism.

---

# Error Handling

Authentication errors are converted into safe user-facing messages.

The Frontend does not directly display raw backend exception information.

Examples include:

| Situation | User-facing message |
|---|---|
| Invalid data | `Los datos proporcionados no son válidos.` |
| Invalid credentials | `Correo o contraseña incorrectos.` |
| Too many attempts | `Demasiados intentos. Inténtalo nuevamente más tarde.` |
| Server failure | `El servicio no está disponible temporalmente. Inténtalo nuevamente más tarde.` |
| Connection failure | `No se pudo conectar con el servicio. Verifica tu conexión e inténtalo nuevamente.` |

Technical information such as the following must not be shown in the user interface:

```text
Traceback
TokenError
DatabaseError
IntegrityError
Internal Server Error
Failed to fetch
Connection refused
Internal service details
```

---

# Security Considerations

The current implementation reduces unnecessary token exposure by:

- Centralizing token storage.
- Centralizing token retrieval.
- Avoiding direct token manipulation from individual pages.
- Automatically adding the access token to API requests.
- Avoiding token values in the user interface.
- Clearing the authentication state when refresh fails.
- Avoiding raw technical backend errors.

The current token strategy uses browser storage because the authentication backend returns JWT tokens in the response body.

A future strategy based on secure `HttpOnly` cookies would require coordinated changes in:

```text
Frontend
API Gateway
Identity microservice
```

and is outside the current HU-032 scope.

## Summary

The Kora Frontend authentication architecture uses the API Gateway as the single backend entry point.

Registration and login use:

```text
POST /api/identity/users/register/
POST /api/identity/users/login/
```

Session renewal uses:

```text
POST /api/identity/users/token/refresh/
```

The Frontend centrally manages:

```text
User information
Access token
Refresh token
```

through `KoraApi`, allowing authenticated requests and session renewal without requiring individual pages to directly manipulate authentication tokens.
