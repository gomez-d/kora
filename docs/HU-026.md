# HU-026 — Token Renewal and Rotation

## 1. Overview

**User Story:** HU-026 — Token Renewal and Rotation

**Microservice:** `svc-identity`

**Technology:** Django REST Framework, SimpleJWT, PostgreSQL

The purpose of this functionality is to maintain authenticated user sessions by allowing access tokens to be renewed through refresh tokens.

The implementation uses JSON Web Tokens (JWT) with automatic refresh token rotation and invalidation of previously used refresh tokens.

## 2. Token Renewal Policy

The authentication system follows the following policy:

| Feature | Configuration |
|---|---|
| Access token lifetime | 15 minutes |
| Refresh token lifetime | 1 day |
| Refresh token rotation | Enabled |
| Blacklist after rotation | Enabled |
| Renewal mechanism | Refresh token |
| Expired refresh token | New login required |
| Reused refresh token | Rejected |

### JWT Configuration

The following configuration is defined in Django's `settings.py`:

```python
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=15),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=1),
    "ROTATE_REFRESH_TOKENS": True,
    "BLACKLIST_AFTER_ROTATION": True,
    "ALGORITHM": "HS256",
    "SIGNING_KEY": os.getenv("JWT_SIGNING_KEY"),
}
```

The `ROTATE_REFRESH_TOKENS` option generates a new refresh token after a successful renewal.

The `BLACKLIST_AFTER_ROTATION` option invalidates the refresh token used in the renewal request.

## 3. Refresh Token Blacklist

The SimpleJWT blacklist application is enabled in `INSTALLED_APPS`:

```python
INSTALLED_APPS = [
    # Existing applications
    'rest_framework_simplejwt.token_blacklist',
]
```

The database migrations were successfully applied using:

```bash
python manage.py migrate
```

The blacklist application stores outstanding and invalidated refresh tokens in the database.

This prevents previously used refresh tokens from being reused after rotation.

## 4. API Endpoint

### Refresh Access Token

| Property | Value |
|---|---|
| HTTP Method | POST |
| Endpoint | `/api/users/token/refresh/` |
| Content-Type | `application/json` |
| Authentication | Refresh token required |

**Request body:**

```json
{
    "refresh": "CURRENT_REFRESH_TOKEN"
}
```

**Successful response — HTTP 200 OK:**

```json
{
    "access": "NEW_ACCESS_TOKEN",
    "refresh": "NEW_REFRESH_TOKEN"
}
```

The response contains a new access token and a new refresh token.

The previous refresh token is added to the blacklist and can no longer be used.

### Error Responses

| HTTP Status | Description |
|---|---|
| 401 Unauthorized | Invalid refresh token |
| 401 Unauthorized | Expired refresh token |
| 401 Unauthorized | Blacklisted or previously used refresh token |
| 400 Bad Request | Missing or malformed request data |

## 5. Token Renewal Workflow

The renewal process follows these steps:

1. The user authenticates through the login endpoint.
2. The identity service issues an access token and a refresh token.
3. The access token is used to access protected endpoints.
4. When the access token expires, the client sends the current refresh token to the renewal endpoint.
5. SimpleJWT validates the refresh token.
6. A new access token and refresh token are generated.
7. The previous refresh token is added to the blacklist.
8. The client stores and uses the new tokens for subsequent requests.

If the refresh token has expired, been invalidated, or is invalid, the service rejects the request and the user must authenticate again.

## 6. API Gateway Integration

The refresh endpoint is exposed through the API Gateway:

```http
POST /api/users/token/refresh/
```

The endpoint must be accessible without a valid access token because its purpose is to renew an expired access token.

However, the refresh token included in the request body must be valid.

The API Gateway forwards the request to `svc-identity`, where SimpleJWT performs token validation and rotation.
