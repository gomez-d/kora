# HU-002 — API Gateway Routing and Proxy

## Objective

Implement the API Gateway routing mechanism that allows external clients to access the Identity and Business microservices without exposing their internal URLs.

The API Gateway acts as the single backend entry point and is responsible for routing requests to the corresponding internal microservice.

## Service Ports

For the local development environment, the following ports were defined:

| Component   |   Port | Purpose                    |
| ----------- | -----: | -------------------------- |
| API Gateway | `8000` | Public backend entry point |
| Identity    | `8001` | Identity microservice      |
| Business    | `8002` | Business microservice      |

The corresponding internal service URLs are configured through environment variables:

```env
IDENTITY_SERVICE_URL=http://localhost:8001
BUSINESS_SERVICE_URL=http://localhost:8002
```

This configuration prevents internal service addresses from being hardcoded into the Gateway logic.

## Implemented Tasks

### T01 — Define public API Gateway routes

The public routing structure of the API Gateway was defined using Django URL configuration.

The Gateway exposes the following base routes:

```text
/api/identity/
/api/business/
```

Each route acts as the entry point for requests intended for its corresponding microservice.

The routing structure allows the Gateway to determine the destination of each request without exposing the internal service URLs to external clients.

### T02 — Configure Identity internal URL

The internal URL of the Identity microservice was configured through the environment variable:

```env
IDENTITY_SERVICE_URL=http://localhost:8001
```

The value is loaded through Django settings and used by the Gateway when communicating with Identity.

This approach allows the service address to change between environments without modifying the application code.

### T03 — Configure Business internal URL

The internal URL of the Business microservice was configured through:

```env
BUSINESS_SERVICE_URL=http://localhost:8002
```

As with Identity, the value is managed through environment configuration.

### T04 — Implement Identity proxy

A generic proxy mechanism was implemented for the Identity microservice.

The Gateway receives requests through:

```text
/api/identity/<path>
```

and forwards the corresponding path to Identity.

For example:

```text
GET /api/identity/users/health/
```

is forwarded internally as:

```text
GET http://localhost:8001/api/users/health/
```

The proxy uses Django REST Framework's `dispatch()` method to process requests independently of the HTTP method.

### T05 — Implement Business proxy

The Business microservice follows the same proxy pattern as Identity.

Requests received through:

```text
/api/business/<path>
```

are forwarded to the Business microservice using its configured internal URL.

This provides a consistent routing mechanism for both microservices.

### T06 — Propagate HTTP methods, parameters, body and responses

A reusable HTTP forwarding function was implemented:

```python
forward_request()
```

This function uses the `requests` library to communicate with the target microservice.

The following request information is propagated:

* HTTP method (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, etc.).
* Relevant HTTP headers.
* Query parameters.
* JSON request body.

The Gateway also propagates the microservice response by preserving:

* Response content.
* HTTP status code.
* Content type.

The generic forwarding mechanism allows the same proxy implementation to support multiple HTTP methods without creating a separate view for each method.

### DRF Request Processing

Because the proxy overrides `APIView.dispatch()`, the normal DRF request initialization must be performed explicitly.

The Gateway converts Django's original request into a DRF `Request` and executes the initial DRF processing before forwarding the request.

This allows the proxy to access information such as:

```python
request.method
request.headers
request.query_params
request.data
```

while preserving the initial DRF processing related to authentication, permissions and throttling.

### T07 — Basic routing and communication error handling

Two basic error scenarios were identified.

#### Non-existent Gateway route

When a requested route does not exist, Django handles the routing error and returns:

```text
404 Not Found
```

For example:

```text
GET /api/identity/route-that-does-not-exist/
```

results in a `404` response.

#### Microservice unavailable

When the Gateway identifies the correct route but cannot communicate with the target microservice, the proxy catches the HTTP communication exception and returns:

```text
503 Service Unavailable
```

Example response:

```json
{
    "error": "Identity service unavailable"
}
```

This distinguishes a routing problem (`404`) from a service availability problem (`503`).

### T08 — Connect Gateway routing with project microservices

The Gateway routing structure was prepared to support the project stories that require communication with Identity and Business.

The final routing pattern is:

```text
/api/identity/<path>
        ↓
Identity microservice

/api/business/<path>
        ↓
Business microservice
```

This approach allows new endpoints to be exposed through the Gateway without implementing a dedicated proxy view for every microservice endpoint.

The specific endpoint validation for HU-003 and HU-006 will be performed as the corresponding microservice endpoints become available.

## Final Architecture Flow

```text
                         API Gateway
                         localhost:8000
                              │
                 ┌────────────┴────────────┐
                 │                         │
        /api/identity/<path>      /api/business/<path>
                 │                         │
                 ▼                         ▼
        Identity :8001              Business :8002
```

External clients communicate only with the API Gateway.

The Gateway is responsible for routing requests to the appropriate internal microservice.

## Responsibilities

### API Gateway

The API Gateway is responsible for:

* Providing the public backend entry point.
* Routing requests to the appropriate microservice.
* Hiding internal microservice URLs.
* Forwarding HTTP request information.
* Returning microservice responses.
* Handling basic communication failures.

### Identity Microservice

Identity remains responsible for:

* User identity management.
* Authentication.
* Authorization and related identity functionality.
* Identity-related business logic.

### Business Microservice

Business remains responsible for:

* Nutritional profiles.
* Food-related functionality.
* Consumption and nutritional calculations.
* Business-related logic.

The Gateway does not implement the business logic of either microservice.

## Validation

The Gateway-to-Identity communication was successfully validated using the Identity health endpoint.

The dynamic routing was validated with:

```text
GET /api/identity/users/health/
```

which was successfully forwarded to:

```text
GET /api/users/health/
```

The Gateway also successfully returned the response received from Identity.

The routing error behavior was validated by requesting a non-existent route and receiving:

```text
404 Not Found
```

The service availability handling was also implemented so that communication failures result in:

```text
503 Service Unavailable
```

The Business proxy follows the same architecture and will be validated independently once its implementation is completed.

## Result

The API Gateway now provides a centralized routing layer between external clients and the Kora microservices.

The implementation establishes the following communication model:

```text
Client
   │
   ▼
API Gateway :8000
   │
   ├──────────────► Identity :8001
   │
   └──────────────► Business :8002
```

This keeps the microservices' internal URLs hidden from external clients and establishes the API Gateway as the single backend entry point.
