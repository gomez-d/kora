
# HU-070 — Password Recovery

## 1. Objective

Implement a password recovery workflow in Kora that allows users to request recovery instructions and set a new password without an authenticated session.

The workflow integrates the frontend, API Gateway, and Identity microservice. It includes recovery token validation, abuse prevention, and security event auditing through the mechanism implemented in HU-037.

## 2. Implementation

The password recovery process consists of two operations:

1. A user submits an email address through the recovery request interface.
2. If the account exists, the Identity service creates a recovery token and sends recovery instructions using the configured email backend.
3. The user opens the recovery link and submits a new password.
4. The Identity service validates the token and password, updates the stored password, and consumes the token.

The frontend communicates with the Identity service through the API Gateway rather than calling the microservice directly.

**Main implementation files:**

| Component | File | Responsibility |
|---|---|---|
| Identity | `svc-identity/users/models.py` | Recovery token storage and validation. |
| Identity | `svc-identity/users/serializers.py` | Request and password validation. |
| Identity | `svc-identity/users/views.py` | Recovery request and confirmation endpoints. |
| Identity | `svc-identity/users/throttles.py` | Recovery request rate limiting. |
| Identity | `svc-identity/clients/unstructured_data_client.py` | Security audit event delivery and error logging. |
| Frontend | `frontend/forgot-password.html` | Recovery request form. |
| Frontend | `frontend/reset-password.html` | Password reset confirmation form. |
| Frontend | `frontend/js/kora-password-reset.js` | Form validation and submission handling. |
| Frontend | `frontend/js/kora-api.js` | API Gateway request methods. |
| Frontend | `frontend/js/kora-config.js` | Public recovery endpoint configuration. |

The API Gateway exposes the Identity endpoints through its existing proxy routing mechanism. The recovery endpoints are public and do not require a JWT.

## 3. API Endpoints

### 3.1 Request Password Recovery

**Method:** `POST`

**API Gateway endpoint:** `/api/identity/users/password-reset/`

**Identity service endpoint:** `/api/users/password-reset/`

**Authentication:** Not required.

**Request payload:**

```json
{
    "email": "user@example.com"
}
```

**Successful response — HTTP 200:**

```json
{
    "success": true,
    "message": "If the email exists, password recovery instructions will be sent."
}
```

This generic response is used to avoid disclosing whether an email address belongs to an account.

### 3.2 Confirm Password Recovery

**Method:** `POST`

**API Gateway endpoint:** `/api/identity/users/password-reset/confirm/`

**Identity service endpoint:** `/api/users/password-reset/confirm/`

**Authentication:** Not required.

**Request payload:**

```json
{
    "token": "<recovery-token>",
    "new_password": "<new-password>"
}
```

**Successful response — HTTP 200:**

```json
{
    "success": true,
    "message": "Password reset successfully."
}
```

**Invalid or expired token — HTTP 400:**

```json
{
    "success": false,
    "message": "The password reset token is invalid or has expired."
}
```

### 3.3 Error Responses

| HTTP status | Meaning | Notes |
|---|---|---|
| 200 | Request or confirmation completed. | The recovery request response remains generic. |
| 400 | Invalid input or invalid/expired recovery token. | Password validation errors may have a different response body. |
| 429 | Request throttled. | May be enforced by the API Gateway or Identity service. |
| 500 | Internal server error. | Investigate service logs; do not expose internal details to end users. |

## 4. Abuse Prevention and Token Security

### 4.1 Rate Limiting

The Identity service applies these rate limits:

| Operation | Scope | Limit |
|---|---|---|
| Recovery request | Client IP | 5/hour |
| Recovery request | Normalized email address | 3/hour |
| Recovery confirmation | Client IP | 10/hour |

Email addresses are normalized with `strip()` and `casefold()` before a SHA-256 hash is used to construct the account throttle cache key. Rate-limit counters use Django's PostgreSQL-backed `DatabaseCache` in the local configuration reviewed during development.

The API Gateway also has recovery-specific throttling settings. Its effective deployment configuration and trusted proxy behavior must be verified separately.

### 4.2 Recovery Token Handling

`PasswordResetToken` stores a token hash, expiration time, usage flag, associated user, and creation time. The raw recovery token is used only to complete the recovery operation and should never be logged or committed to source control.

The confirmation workflow:

1. Validates the submitted token.
2. Validates the new password against Django's configured password validators.
3. Updates the user's password through Django's password hashing mechanism.
4. Consumes the recovery token after the password update.
5. Schedules the successful recovery audit event after the database transaction commits.

The model-level tests confirmed that a consumed token is rejected by `get_valid_token()`.

### 4.3 Frontend Controls

The frontend implementation:

- Accepts email addresses through a recovery request form.
- Displays a generic success message after an accepted request.
- Retrieves the recovery token from the URL query string.
- Removes the token from the visible URL using `history.replaceState()`.
- Does not store the recovery token in `localStorage` or `sessionStorage`.
- Disables submission when the recovery token is absent.
- Checks the new password and confirmation input for a match.
- Prevents repeated submissions while a request is pending.
- Displays user-friendly errors for invalid requests, throttling, and service failures.

## 5. Security Event Auditing

Password recovery uses the centralized security event logging mechanism documented in [HU-037 — Security Event Logging](HU-037-SECURITY-LOGGING.md).

The Identity service submits events to the Unstructured Data service, which persists the audit records in MongoDB.

| Event | Level | Source | Description |
|---|---|---|---|
| `password_reset_requested` | INFO | `password_reset_request` | Recovery request processed. |
| `password_reset_rate_limited` | WARNING | `password_reset_request` or `password_reset_confirm` | Identity service request rejected by throttling. |
| `password_reset_invalid_token` | WARNING | `password_reset_confirm` | Invalid or expired token submitted. |
| `password_reset_completed` | INFO | `password_reset_confirm` | Password successfully reset. |

The audited events do not include raw recovery tokens or passwords. Delivery errors are handled by the audit client, and warning logging was added for handled delivery failures.

**MongoDB verification example:**

```javascript
db.logs.find({
    service: "svc-identity",
    event: { $in: [
        "password_reset_requested",
        "password_reset_rate_limited",
        "password_reset_invalid_token",
        "password_reset_completed"
    ] }
}).sort({ timestamp: -1 })
```

## 6. Configuration Requirements

### 6.1 Identity Service

| Setting | Purpose |
|---|---|
| `SECRET_KEY` | Django application secret. |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` | Identity PostgreSQL connection. |
| `DB_PASSWORD` or `DB_PASSWORD_FILE` | Identity database credentials. |
| `UNSTRUCTURED_DATA_SERVICE_URL` | Internal audit service base URL. |
| `UNSTRUCTURED_DATA_SERVICE_TOKEN` | Internal audit service authentication. |
| `FRONTEND_PASSWORD_RESET_URL` | Base URL for the password recovery link. |
| `MAILERS` | Django 6.1 email backend configuration. |
| `REST_FRAMEWORK.DEFAULT_THROTTLE_RATES` | Password recovery rate limits. |
| `CACHES` | Shared Identity rate-limit counter storage. |

In the local development environment, Django's console email backend was configured using `MAILERS`:

```python
MAILERS = {
    "default": {
        "BACKEND": "django.core.mail.backends.console.EmailBackend",
    }
}
```

This configuration prints recovery email content in the Identity service console. It is intended for development and is not a production delivery mechanism.

### 6.2 Local Development Service Addresses

| Component | Address |
|---|---|
| Frontend | `http://localhost:5500` |
| API Gateway | `http://localhost:8080` |
| Identity service | `http://127.0.0.1:8001` |
| Unstructured Data service | `http://127.0.0.1:8003` |

These values describe the tested local arrangement; containerized deployments may use different internal hostnames and ports.

The API Gateway's Identity service URL must target the active Identity service. Frontend API requests should target the Gateway, not the Identity service directly.

### 6.3 Deployment Security Considerations

- Protect internal services from direct untrusted access.
- Trust forwarded client-IP headers only from controlled proxies; review `NUM_PROXIES` and header handling before production.
- Configure HTTPS, allowed hosts, and browser cross-origin behavior for the deployed environment.
- Keep authentication keys, internal service tokens, and database credentials out of version control.
- Review rate limiting under concurrent requests; Django REST Framework's default throttling does not provide strict atomic guarantees.

For broader configuration conventions, see [Configuration and Secrets](../security/CONFIGURATION_AND_SECRETS.md).

## 7. Tests Performed

Manual tests were performed during HU-070-T04 through HU-070-T07 using PowerShell, Django Shell, browser developer tools, PostgreSQL, and MongoDB audit queries.

| Test | Expected result | Observed result | Status |
|---|---|---|---|
| Recovery request through API Gateway | HTTP 200 and generic response. | HTTP 200 and generic response returned. | Passed |
| Recovery request from frontend | Request sent to Gateway and success feedback displayed. | HTTP 200, form reset, generic success message. | Passed |
| Confirm with valid token through frontend | HTTP 200 and password reset confirmation. | HTTP 200 and success message; fields cleared. | Passed |
| Validate password update | New password accepted for test account. | Django model-level password check succeeded during previous testing. | Passed |
| Open reset form without token | Submission blocked with an error message. | Button disabled and missing-token message displayed. | Passed |
| Reject an unknown token | `get_valid_token()` returns `None`. | Unknown token rejected. | Passed |
| Consume and reuse a token at model level | Token becomes invalid after `consume()`. | Initially valid, consumed successfully, then rejected. | Passed |
| Persist token consumption | `used` flag stored in PostgreSQL. | Latest frontend test token had `used=True`. | Passed |
| Request throttling | Excessive requests receive HTTP 429. | HTTP 429 observed; Identity cache counters inspected. | Passed |
| Invalid-token audit | Warning event stored in MongoDB. | `password_reset_invalid_token` event found. | Passed |
| Rate-limit audit | Warning event stored in MongoDB. | Request and confirmation rate-limit events found. | Passed |
| Successful recovery audit | Completion event stored in MongoDB. | `password_reset_completed` event found. | Passed |

The token consumption and reuse test directly exercised the model methods; it was not an endpoint-level replay test.

## 9. Result

The Kora password recovery workflow was implemented and manually validated across the frontend, API Gateway, Identity service, and the HU-037 auditing infrastructure.

The completed tests support successful recovery requests, password reset confirmation, model-level single-use token validation, request throttling, and persistence of security audit events.

The remaining automated, concurrency, and deployment-specific checks should be completed before treating the workflow as production-ready.
