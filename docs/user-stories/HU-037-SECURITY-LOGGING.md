# **HU-037 — Security Event Logging**

## **1. Objective**

Implement centralized security event logging in the Kora Identity microservice, allowing relevant authentication and authorization events to be recorded and stored in the Unstructured Data microservice.

The implementation aims to provide traceability of security-related operations while ensuring that sensitive information is not stored in event records.

## **2. Implementation**

A communication mechanism was implemented between the Identity and Unstructured Data microservices.

The Identity service uses a dedicated client located in:

`svc-identity/clients/unstructured_data_client.py`

The `send_identity_event` function sends security events through an HTTP POST request to the Unstructured Data service.

The implementation includes:

- A standardized event payload.
- Internal service authentication using a shared token.
- A request timeout of 2 seconds.
- Handling of connection errors, timeouts, HTTP errors, and invalid JSON responses.
- Non-blocking behavior regarding the main authentication and authorization operations when the logging service is unavailable.

The internal authentication mechanism uses the `UNSTRUCTURED_DATA_SERVICE_TOKEN` environment variable, configured independently in both services.

The token must remain confidential and must not be committed to version control.

## **3. Implemented Security Events**

The following events are recorded by the Identity service:

| Event | Level | Description |
|---|---|---|
| `user_registered` | INFO | A new user has been successfully registered. |
| `login_failed` | WARNING | An authentication attempt failed. |
| `token_revoked` | INFO | A refresh token was successfully revoked during logout. |
| `invalid_token_attempt` | WARNING | An invalid, expired, or mismatched refresh token was submitted during logout. |
| `access_denied` | WARNING | An authenticated user attempted to access a resource without the required authorization. |

Authorization failures are recorded through the custom DRF exception handler and explicit logging in the RBAC user roles query endpoint.

## **4. Event Structure**

All security events follow a standardized structure.

**Example event payload:**

```json
{
    "user_id": "USER-UUID",
    "event": "login_failed",
    "level": "WARNING",
    "data": {},
    "metadata": {
        "source": "user_login"
    }
}
```

The event structure contains the following fields:

| Field | Description |
|---|---|
| `user_id` | UUID of the associated user. Can be null for anonymous events. |
| `event` | Identifier describing the security event. |
| `level` | Event severity level. |
| `data` | Additional event information. |
| `metadata` | Contextual information about the event source and operation. |

The receiving service adds the event timestamp and identifies the originating service.

## **5. Implemented Endpoint**

The Unstructured Data service exposes an endpoint for receiving security events.

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/documents/identity-events/` | Receives and stores security events generated by the Identity service. |

The endpoint is implemented through `IdentityEventView`.

It validates the internal Bearer token before processing the request.

Requests with invalid or missing authentication credentials are rejected with HTTP 401.

Invalid event payloads are rejected with HTTP 400.

## **6. Event Validation and Security**

The `IdentityEventSerializer` validates incoming event information before storage.

The implementation includes:

- UUID validation for `user_id`.
- Dictionary validation for `data` and `metadata`.
- Default empty dictionaries when optional event information is omitted.
- Rejection of sensitive field names, including `password`, `token`, `access_token`, `refresh_token`, `authorization`, and `secret`.

The same sensitive-field validation is applied to both `data` and `metadata`.

Authentication credentials and sensitive information must not be included in event payloads.

Login failure events do not include the submitted email address or password.

Token revocation events do not include the refresh token.

## **7. MongoDB Storage**

Security events are stored in MongoDB by the Unstructured Data microservice.

The database used is:

`kora_unstructured`

The collection used is:

`logs`

Each stored document contains:

```json
{
    "service": "svc-identity",
    "level": "WARNING",
    "event": "login_failed",
    "data": {
        "user_id": null
    },
    "metadata": {
        "source": "user_login"
    },
    "timestamp": "UTC_TIMESTAMP"
}
```

The timestamp is generated by the receiving service using UTC.

The `user_id` is stored inside the `data` object, while the event name, severity level, originating service, metadata, and timestamp are stored as separate document fields.

## **8. Error Handling and Service Availability**

The logging mechanism was designed to avoid interrupting the main Identity service operations when the Unstructured Data service is unavailable.

The client handles the following communication failures:

| Error | Handling |
|---|---|
| Request timeout | Returns a timeout error. |
| Connection failure | Returns a service unavailable error. |
| Other request exceptions | Returns a communication error. |
| HTTP error response | Returns an invalid response error. |
| Invalid JSON response | Returns an invalid JSON response error. |

The client does not propagate these handled request exceptions to the calling authentication or authorization operation.

The HTTP request uses a 2-second timeout to limit the time spent waiting for the logging service.

## **9. Tests Performed**

Manual tests were performed using PowerShell, Python inside Docker containers, and MongoDB Shell while the services were running through Docker Compose.

| Test | Expected Result | Result |
|---|---|---|
| Failed login attempt | Returns HTTP 401 and records `login_failed`. | Passed |
| Unauthorized RBAC access | Returns HTTP 403 and records `access_denied`. | Passed |
| Successful logout | Revokes the refresh token and records `token_revoked`. | Passed |
| Request without internal authentication | Rejects the request with HTTP 401. | Passed |
| Sensitive information in `data` | Rejects the event with HTTP 400. | Passed |
| Sensitive information in `metadata` | Rejects the event with HTTP 400. | Passed |
| Storage of rejected sensitive events | Does not insert the rejected events into MongoDB. | Passed |
| Unstructured Data service unavailable | Identity login continues successfully. | Passed |
| Service restoration | Unstructured Data service starts successfully again. | Passed |

The event records were inspected directly in the MongoDB `logs` collection to verify successful storage and the absence of rejected test events.

## **10. Running with Docker**

To rebuild the Identity and Unstructured Data containers:

```bash
docker compose up -d --build svc-identity svc-unstructured-data
```

To view the Identity service logs:

```bash
docker compose logs -f svc-identity
```

To view the Unstructured Data service logs:

```bash
docker compose logs -f svc-unstructured-data
```

To access the MongoDB database:

```bash
docker compose exec mongo mongosh kora_unstructured
```

To inspect security events:

```javascript
db.logs.find({ service: "svc-identity" }).sort({ timestamp: -1 })
```

## **11. Result**

Security event logging was implemented within the Kora Identity and Unstructured Data microservices.

The implementation provides centralized storage of authentication and authorization events in MongoDB, internal service authentication, event validation, and protection against logging sensitive field names.

The performed tests verified successful event registration, rejection of unauthorized and invalid requests, protection against sensitive information storage, and continued Identity service operation when the logging service is unavailable.
